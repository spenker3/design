# design

The user's personal design language, worked out as a demo site and component library. Goal: refine the style here, then turn the finished version into a Claude skill that applies it to any project (web, and native apps like GPUI/Qt via the tokens). It may later be packaged as a component library.

## Stack
- Vite + React + TypeScript, plain CSS. Chosen as the easiest for agents to read and write: one token file, semantic classes, thin React wrappers only where behavior is needed. No Tailwind, no component library dependency; native `<dialog>`, `popover`, and form inputs instead.
- Icons: `lucide-react` (16px, stroke 1.75). Mono font: `@fontsource-variable/geist-mono`. UI font: system Helvetica stack (Nimbus Sans / TeX Gyre Heros on Linux), not bundled.
- Specialty deps: `katex` (LaTeX), `pele` (Mermaid syntax to SVG, themed by `--pele-*` CSS variables; chosen over Mermaid for size and CSS theming), `d3-force` (force graph layout). Showcase-only: `marked` (renders the skill's markdown on the Skill page).

## Commands
- `npm run dev`: Vite on :5180. The user may already be running it; check before starting one.
- `npm run build`: `tsc --noEmit` and `vite build`. The only check so far (no tests).
- `npm run skill`: regenerates the skill's generated parts from the repo (`node scripts/skill.ts`; Node 26 runs the TS directly). Warns when a page has no route or a good writing example fails `check()`. Runs on its own at commit; run it by hand only to preview the skill.
- Visual check: `npx vite preview --port 5181`, then `chromium --headless=new --blink-settings=preferredColorScheme=0|1 --window-size=W,H --screenshot=... http://localhost:5181/#/<page>` (0 = dark, 1 = light). Stop the preview afterwards.

## Layout
- `src/design/`: the design system. `index.css` imports everything; `tokens.css` holds the whole language. Then `base.css` (element defaults and inline text elements), one file per component family, each matching one showcase page: `controls.css` (buttons, `kbd`, `.link`, fields, checks, switches, segmented, range, `.cells`, `.swatches-pick`, `.mini-field`, `.otp`, dropzone, `.form-grid`), `navigation.css` (tabs, nav, topbar, workspaces, breadcrumbs, pagination, steps, `.shell`), `content.css` (cards, badges, tags, dots, avatars, table, list, stat, progress, skeleton, empty, `.dl`, `.accordion`, `.callout`, `.banner`, `.msg`/`.composer`), `overlays.css` (toast, dialog, sheet, menu, popover, tooltip, palette, and the floating chrome `.toolbar`/`.panel`/`.dock` over a `.canvas`), `documents.css` (code blocks, diff/terminal, `.tk-*` syntax classes colored by `--code-*` tokens, figures, `.equation`, `.theorem`/`.proof`, `.abstract`, `.refs`), `charts.css` (`.bars`, `.chart`/`.legend`/`.spark`/`.heat`, `.force`, `.nodes`, and `.diagram` which maps `--pele-*` onto the tokens), and `layout.css` (`.stack`, `.row`, `.grid`, `.prose`) imported last so utilities beat component defaults. Each file's header comment lists its classes and when to use them.
- `src/design/writing.ts`: the writing guide as data: `voice`, `mechanics`, and `elements` (each text element's length limit, case, ending, rules, good examples, and bad examples with the reason). `check()`/`measure()` test a string against an element. The Writing page renders and checks it; edit the guide here, not in the page.
- `src/components/`: React only for behavior: `Dialog` (also sheets and the palette), `Menu` (popover + arrow keys), `Toast` (provider + `useToast`), `Choice` (`Segmented`, `Tabs`), `CodeBlock` (head, line numbers, highlights, diff, terminal) with a small regex highlighter in `highlight.tsx`. Specialty: `Tex` (KaTeX), `NodeEditor` (draggable node cards with typed ports), `ForceGraph` (Obsidian-style note graph), `LineChart` (plus `useWidth` for SVG charts that keep text at real size), `Diagram` (Pele `mountAsync`, loads each diagram type lazily).
- `src/site/`: the showcase, which isn't part of the system. Hash routes in `routes.ts`, pages in `pages/`, `Demo`/`Page` wrappers in `Demo.tsx`, showcase-only styles in `site.css` (including the `.media` image stand-in). Ten pages in three nav groups: Language (Principles, Foundations, Writing), Components (Controls, Navigation, Content, Overlays) and Specialty (Documents, Charts & graphs, Terminal), plus a Screens group listing the templates. Keep it that way: a new piece joins the page for its family rather than getting its own page, and related pieces share one `Demo` with bulleted rules. Each `Demo` has two texts. `rules` is what the site shows: a sentence or two on what the preview can't show (when to use it, behavior, constraints), never a description of what's visible. `spec` is never rendered: it's the full usage text for the skill, which can't see the preview, and replaces `rules` there. When a demo needs both, `rules` condenses `spec`, so edit both when a decision changes. Demo copy should be neutral content, not text explaining the design. The Skill page (`pages/Skill.tsx`, `#/skill`) renders `skill/` live via `import.meta.glob`; it's pinned above the nav, outside `routes`, and has no `Demo`s so the generator ignores it.
- `src/site/pages/Terminal.tsx` (`#/terminal`): the language in a terminal, drawn with `src/site/Tty.tsx`, a showcase-only cell renderer (lines of `[text, attrs]` segments; `box`, `beside`, `row`, `fit`, `spread`, `hints`; `beside` sizes each column by its first line). Its `.tty` styles in `site.css` use the GeistMono Nerd Font first, since plain Geist Mono lacks block and braille glyphs. Rules feed `skill/references/tui.md`.
- `src/site/templates/`: full-screen example UIs at `#/t/<name>`, one per screen arrangement in the skill: chat (app shell), dashboard (data), settings (forms), canvas (work surface), article (reading), landing (marketing). Registered in `templates/index.ts` and `routes.ts`. They render without the showcase chrome; a floating `.template-bar` (bottom right) goes back and switches theme. The showcase stays mounted (hidden) under a screen, so leaving one (back button, Esc, or a template's wordmark) returns to the same page and scroll position; `leaveScreen()` in `routes.ts` handles it. `templates.css` holds only their arrangement; looks come from the system. If a template needs a new look, add it to `src/design/`, not here.

## The language (agreed decisions)
- Black and white first. Primary = the inverted block (black on white in light, white on black in dark); secondary is the reverse. Gray for structure, color for meaning, used wherever it helps, buttons included.
- **Selection is always the inverted block** (`--sel-bg`/`--sel-fg`): tabs, nav, table/list rows, menu cursor, pressed toggles, checked inputs, text selection. No accent color for selection. Empty/unused items drop to 50% opacity.
- Code blocks have no divider and no copy button. The head (file, then language) is the first row of the code, unnumbered, starting where the line numbers do. The language name takes its palette hue (rust orange, ts blue, ...); shell and unknown languages stay faint, and green and red never name a language.
- Chart series use `--series-1..4` (blue, orange, violet, yellow), an order validated for color blindness in both themes; the palette order itself puts red next to orange. One series is fg.
- Radius 4px (`--radius`), 2px for small parts; round only for avatars, dots, radios. Chosen over 0px and 8px.
- No shadows. 1px lines; overlays are bg with a 1px fg border, plus a light scrim when modal.
- Helvetica everywhere, Geist Mono only for code, keys, and numbers compared down a column (table figures, prices, IDs). Other numbers (counts, page/step numbers, axes, citations) stay Helvetica with tabular figures, never zero-padded. 14px base, 32px controls (44px on touch). Almost no motion (80–140ms).
- The user's own native apps, Omarchy apps included, use this design rather than the Omarchy theme: token colors, no theme accent, 4px radius regardless of Hyprland. Only the theme's light/dark `mode` is followed.
- Colors use `light-dark(LIGHT, DARK)` in `tokens.css`, so every token is set for both themes on one line. Theme follows the system; `data-theme="light"|"dark"` on `<html>` forces one.

## Conventions
- Every good example in `writing.ts` must pass `check()` for its element, and every bad one carries a reason. The Writing page flags a good example that fails.
- Components carry no outer margin; layouts set `--gap`.
- State goes in ARIA attributes, not modifier classes: `aria-selected`, `aria-current`, `aria-pressed`, `aria-invalid`, `aria-busy`.
- New colors go in `tokens.css` with both values; components never use raw hex.
- Floating chrome that stays on screen (toolbar, panel, dock) uses `--line-strong`; transient overlays (menu, dialog, toast) use the fg border.
- The repo is meant to be public. Demo and example text stays neutral: no real names, usernames, private projects, courses, or brands. The stock cast is a made-up project tool `atlas` (files, tasks, milestones), shop orders, an `ops` service monitor in the TUI pages, and Mira Chen (`mira`, `mc`) as the person.

## The design skill
- `skill/` is the Claude skill `design`, symlinked globally as `~/.claude/skills/design`, so every project reads it live from this repo.
- Everything in `skill/` is generated; never edit it. The skill's prose (the idea, roles, the derivation procedure, never-list, screen recipes, how to apply it) lives in `src/design/skill.md`, which renders to `skill/SKILL.md`. Write any value that comes from a token as a placeholder (`{{radius}}`, `{{touch.control}}`, `{{mono}}`, `{{series}}`; the full list is above `renderSkill` in `scripts/skill.ts`), never as a literal, so token edits can't leave the prose stale. The skill links to the repo on GitHub, never to a local path, so it works on any machine: `{{repo}}` is the URL (from `repository` in `package.json`) and `{{repo:src/design/}}` renders a link to a path (end folders with `/`; a missing path stops the build). Links point at `main`, so they show what's pushed. An unknown or theme-dependent placeholder stops the build.
- The skill is framework-agnostic: rules are stated as ideas, with the CSS spelling in parentheses at most. No toolkit API code (GPUI, QML, ratatui) in it; only decisions a medium forces (terminal, Omarchy) get their own rules. The CSS in `src/design/` is offered as a web shortcut, not as the language.
- `scripts/skill.ts` builds the generated parts from: `tokens.css` (→ `tokens.md`, `tokens.json`), each CSS file's header comment, the `title` and `spec` (or `rules`, when there's no `spec`) props of every element in `src/site/pages/` (Demo, or any wrapper that takes them), `Principles.tsx`, `writing.ts`, `routes.ts` + `templates/index.ts` (→ `screens.md`), and the comment above each export in `src/components/`. It parses JSX by regex, so keep `rules` and `spec` as a string or simple JSX (`<ul><li>`, `<b>`, `<code>`) and keep principles as `["title", "body"]` string tuples. New CSS files land in `components.md` unless mapped in `cssGroup`. A page's rules land in the reference file for its nav group (`refByGroup` in `scripts/skill.ts`: Language → foundations.md, Components → components.md, Specialty → specialty.md), unless `refByTitle` overrides it (Terminal → tui.md; Writing is skipped since writing.md comes from `writing.ts`). Only `spec`/`rules` text reaches the skill, so put mappings there, not in page-body tables.
- The skill updates only at commit, so it always matches a finished, committed design rather than work in progress. The git pre-commit hook (`.githooks/pre-commit`, enabled by `core.hooksPath`, which `npm install` sets via `prepare`) runs the generator and stages `skill/`; a generator error stops the commit. Generated files are only rewritten when their content changes. Between commits `skill/` (and the Skill page) shows the last commit's design.
- Before every commit, review the change against the skill's prose: if it changes or adds an agreed decision (a principle, a role, a never, a screen recipe, how to apply it), update `src/design/skill.md` and "The language" section above in the same commit. The generator can't infer prose, so this is what keeps the skill current.
